# 工程级执行规格生成器

将一句模糊的任务描述，转化为 AI 可直接执行的工程级规格——包含精确的改动边界、量化的约束条件、可执行的验收命令。

不是"优化措辞"，不是"套模板"——是基于项目真实数据（代码分析、历史踩坑、用户习惯）生成让 AI 做出正确决策所需的最小且充分的信息集。

## 何时触发

- 用户输入 `/arise-prompt` + 一段描述
- 用户说「帮我优化这个提示词」「把这个变成提示词」「prompt 一下」
- 用户给出模糊的任务描述，想要更精确的执行方案
- arise-router 路由过来（判断为需要细化的模糊描述）

## 工作流程（三层架构）

```
用户输入简短描述
  ↓
━━━ Layer 1: Context Gathering（数据收集）━━━
  ↓
━━━ Layer 2: Intent Analysis（意图分析）━━━
  ↓
━━━ Layer 3: Spec Assembly（规格组装）━━━
  ↓
展示给用户确认
  ↓
用户确认 → 按规格执行
用户要改 → 调整后执行
用户说不用 → 只输出规格文本，不执行
```

## Layer 1: Context Gathering（数据收集）

**在生成任何规格之前，必须先收集数据。** 这不是可选步骤。

### 1.1 项目元信息

读取 `.arise/context.md`（如存在）：
- 语言、框架、包管理器、测试框架
- 项目约定（commit 语言、分支策略、代码风格）
- 目录结构概要

如果 `context.md` 不存在，尝试从以下来源自动推断：
- `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml`
- 目录结构（src/ tests/ etc.）
- 最近 5 条 git log

### 1.2 用户习惯

读取 `.arise/habits/index.md`（如存在），按当前任务相关性过滤：
- 提取与当前任务类型匹配的习惯条目
- 这些习惯将作为规格中的约束条件

### 1.3 历史踩坑

读取 `.arise/bug-fix-memory/log.md`（如存在），检索相关记录：
- 按关键词 / 涉及文件 / 模块索引匹配
- 命中的条目将提取根因和防范动作

### 1.4 代码分析数据（涉及代码改动时）

当用户输入涉及具体代码时，按优先级获取分析数据：

#### 优先读取 CodeGraph Context

如果 `.arise/codegraph-context.json` 存在（router 已做过预分析）：
- 校验 `taskId` 字段：从 `.arise/context.md` 的「活跃状态 → 当前 taskId」读取当前任务 ID，与 codegraph-context.json 的 `taskId` 字段对比。不匹配（或 context.md 无 taskId）→ 视为不存在，走下方自行调用逻辑
- 直接读取，不重复调用 CodeGraph
- 从中提取：`riskLevel`、`blastRadius`、`httpChain`、`doNotBreak`

如果不存在（prompt 被直接调用，未经 router）：
- 自行调用 CodeGraph `impact_analysis`（可用时）
- 调用成功后，**写入 codegraph-context.json**（按 router 的缓存协议生成 taskId、写入业务字段、同步更新 context.md 的「当前 taskId」字段），确保后续的 verify/commit 能读到预分析数据
- 或回退到下方的 arise-knowledge / 无后端逻辑（无后端时不写 codegraph-context.json，verify/commit 会按降级运行——此时应告知用户：「直接调用 prompt 未走 router 预分析，verify 将使用全量测试命令，建议下次走 `/arise` 获得精准验证」）

#### 有 CodeGraph 时（完整能力）

1. `impact_analysis(目标符号)` — 获取爆炸半径、风险等级、受影响测试
2. `semantic_code_search(自然语言描述)` — 语义搜索相关代码
3. `trace_http_chain(路由路径)` — 追踪 REST API 完整请求流（涉及接口时）
4. `get_call_graph(函数名, depth=2)` — 理解调用关系
5. `dependency_graph(文件)` — 理解文件依赖

数据用途映射：
- `impact_analysis` 的风险等级 + 爆炸半径 → 生成「关注点」和「改动边界」
- `trace_http_chain` 的链路 → 确定执行序列的顺序和层级标注
- `semantic_code_search` 的结果 → 填充「上下文」中的相关代码
- `doNotBreak` 清单 → 直接写入「改动边界」的不可碰区域

#### 有 arise-knowledge 时（基础能力）

1. `search_entities` 或 `search_code` 定位相关实体
2. `get_call_graph` 理解函数的调用关系
3. `get_dependencies` 理解文件的依赖关系
4. `get_module_summary` 获取模块结构概要

#### 无后端时（回退）

1. 根据关键词（接口名、函数名、文件名、模块名）搜索项目
2. 定位相关文件路径、函数/类/接口
3. 提取关键代码片段（不是整个文件）

### 1.5 Git 状态

- 当前分支名
- 是否有未提交改动
- 最近 3 条 commit（了解当前工作方向）

### 1.6 多模态与多源上下文融合（图片、文档、截图、附件）

**铁律：严禁脱离项目的孤立文本润色！**
当用户传入文档（PRD/需求/接口文档）、图片（报错截图/UI设计稿/架构图）或任何附件时，**不得仅对其进行字面润色或提炼简单提示词**。必须做到全上下文深度融合：
1. **图片解析**：读取报错截图中的错误栈、UI截图中的组件结构，并关联匹配项目源码中的对应文件与 CSS/DOM 位置。
2. **文档对齐**：将文档中的 API 字段、业务逻辑与项目已有 `context.md`、类型定义（TypeScript 接口 / Struct）、代码实现进行逐项映射与对齐。
3. **记忆结合**：将文档/图片需求与项目历史踩坑记录 (`bug-fix-memory`) 及个人编码习惯 (`habits`) 交叉比对，识别潜在的盲区与回归风险。

### 收集原则

- **能自动获取的就自动获取**，不要问用户要已经存在于项目中的信息
- **只收集相关的**，不要全量读取所有文件
- **收集失败不阻塞**，任何文件不存在则跳过，不报错
- **拒绝孤立润色**：必须将用户输入（含图文）与当前代码库及记忆库融合为可落地的工程执行规格

### 置信度机制（防幻觉铁律）

**核心原则：只把确实的写进规格，不确实的要么标注要么不写。**

每条收集到的信息都必须分级：

| 置信度 | 条件 | 处理方式 |
|--------|------|----------|
| **确实** | 确实读到了文件内容 / 确实执行了命令看到了输出 | 直接写进规格 |
| **待确认** | 搜索匹配到但未验证内容 / 关键词命中但语义相关性不确定 | 标注「→ 执行时先确认」 |
| **推测** | 没搜到但觉得可能有 / 根据经验猜测 | **禁止写进规格** |

**具体约束：**

1. **文件路径**：只写确实搜索到的文件，不写「觉得应该有」的文件
2. **行号**：不写行号。行号随时会变，写了就是在误导。用函数名/类名定位
3. **代码片段**：只贴确实读到的代码，不要「根据记忆」补充
4. **bug-memo 命中**：如果关键词匹配但语义不确定，标注「可能相关」而不是断言「之前踩过这个坑」
5. **意图分析**：如果无法确定明确度/范围/风险，不写入规格，而是先问用户

## Layer 2: Intent Analysis（意图分析）

从三个维度分析用户意图，决定规格的结构和详细程度：

### 2.1 明确度判断

| 明确度 | 特征 | 处理方式 |
|--------|------|----------|
| 明确 | 用户说了具体要做什么、改哪里、期望结果 | 直接进入 Layer 3 组装 |
| 模糊 | 用户说了方向但缺少关键信息 | 问 1-2 个澄清问题，然后进入 Layer 3 |
| 探索性 | 用户在试探（「这个能不能...」「有没有办法...」） | 先提供选项/方案，确认后再生成规格 |

### 2.2 改动范围判断

| 范围 | 特征 | 影响规格生成 |
|------|------|-------------|
| 单点 | 改一个函数、修一个 bug、加一个字段 | 规格极简（3-5 行），只写目标+验收 |
| 多文件 | 涉及多个文件联动 | 需要改动边界 + 执行序列 |
| 架构级 | 重构、新模块、跨模块改动 | 完整规格，所有模块都需要 |

### 2.3 风险等级判断

优先使用 CodeGraph 返回的 `riskLevel`。如果没有 CodeGraph 数据，按以下规则判断：

| 风险 | 特征 | 影响规格生成 |
|------|------|-------------|
| 低 | 新增代码、不影响现有功能 | 只需目标+验收 |
| 中 | 修改现有逻辑、可能影响其他模块 | 加入改动边界 + 关注点 |
| 高 | 涉及数据库/支付/认证/生产环境 | 完整规格 + 分步验证 + 回滚方案 |

### 2.4 澄清策略

当意图不够明确时，**最多问 2 个问题**：
- 问题要具体（「你要改哪个接口？」而不是「你能说详细点吗？」）
- 如果能从代码上下文推断答案，不要问
- 问完立即进入 Layer 3，不要循环追问

## Layer 3: Spec Assembly（规格组装）

**不套固定模板。** 根据收集到的数据和意图分析结果，按模块化方式组装执行规格。

### 可用模块（6 个）

#### 1. 关注点模块（改动范围 > 单点时必选）

声明本次任务需要关注的具体维度。每个关注点必须：
- **具体**：有数据支撑，不是泛泛的「注重安全」
- **可量化**：能判断是否违反
- **有边界**：说清楚关注到什么程度

来源：
- CodeGraph `blastRadius` → 向后兼容关注点（「N 个调用方依赖当前签名」）
- CodeGraph `httpChain` → 性能/架构关注点（「不阻塞主链路」）
- bug-memo 历史 → 防回归关注点（「上次因为 X 出过事」）
- 任务性质 → 安全/性能/兼容性关注点

**格式：**
```
## 关注点
- <维度>：<具体量化描述>
- <维度>：<具体量化描述>
```

**反面教材 vs 正确写法：**
```
❌ 注重安全性和向后兼容
✅ 向后兼容：33 个调用方依赖 login() 的返回格式 {token, user, redirectUrl}，不能变
✅ 安全性：验证码需要过期机制（5min），同一 IP 每分钟最多请求 10 次
```

#### 2. 改动边界模块（改动范围 > 单点时必选）

明确画出"可以动"和"不能碰"的边界线。

来源：
- CodeGraph `doNotBreak` → 不可碰清单
- CodeGraph `httpChain` → 非目标层级的接口
- CodeGraph `blastRadius.affectedFiles` → 可能受影响的文件（用于画边界）

**格式：**
```
## 改动边界
- 可改：<具体文件/函数>
- 不可碰：<具体文件/函数 + 原因>
- 链路位置：<当前修改在第几层>（如有 HTTP 链路）
```

#### 3. 上下文模块（有相关数据则必选）

只放执行时真正需要知道的信息，不堆砌背景。

内容：
- 技术栈一行（语言 + 框架 + 包管理器 + 测试框架）
- HTTP 链路（用 `→` 连接，方括号标注当前修改层）
- 相关代码路径（用函数名定位，不写行号）
- 历史踩坑摘要（一句话：上次 X 导致 Y，本次确保 Z）

**格式：**
```
## 上下文
- 技术栈：TypeScript + Express + pnpm + vitest
- 链路：rateLimit → validateLogin → [loginHandler] → UserService.verify → DB
- 相关代码：src/api/auth.ts 的 loginHandler()
- 历史踩坑：login 改动曾丢失 redirect 参数（2024-01），确保 redirect 透传
```

#### 4. 目标 + 验收模块（必选）

目标一句话说清楚做什么。验收标准必须是**可执行的验证动作**——能粘贴到终端跑的命令，或能肉眼判断的具体行为。

**格式：**
```
## 目标
<一句话，具体可验证>

## 验收
- `<验证命令>` → <预期结果>
- `<验证命令>` → <预期结果>
- <可观察行为> → <预期表现>
```

**反面教材 vs 正确写法：**
```
❌ 不影响现有登录流程
❌ 确保测试通过
✅ `pnpm vitest run tests/auth.test.ts` → 全通过（0 failed）
✅ `curl -X POST /api/login -d '{"email":"a@b.c","password":"x"}'` → 400 + body 含 "captcha required"
```

#### 5. 执行序列模块（改动范围 > 单点 或 riskLevel >= HIGH 时必选）

每步 = 动作 + 产出 + 验证。HIGH 风险时每步后必须有验证命令。

排序依据（优先级从高到低）：
1. HTTP 链路层级（从底向上或从上向下，根据任务性质决定）
2. 依赖顺序（被依赖的先改）
3. 风险顺序（低风险的先改，确认安全后再改高风险的）

**格式：**
```
## 执行序列
1. <动作> → <产出> → <验证命令>
2. <动作> → <产出> → <验证命令>
3. <动作> → 全量验证通过
```

#### 6. 历史经验模块（bug-memo 命中时必选）

只写根因和防范动作，不写背景故事。一句话格式：

```
## 历史经验
- 上次踩坑：<X 导致 Y>。本次确保 <Z>。
```

### 组装原则

- **信息密度 > 长度**：10 行精准规格优于 50 行模板化输出
- **约束 > 指令**：告诉边界比告诉步骤更有效——模型知道怎么写代码，但不知道哪里不能碰
- **数据 > 描述**：「33 个调用方」比「很多地方在用」有效 10 倍
- **验证命令 > checklist**：「跑 pnpm test」比「确保测试通过」可执行
- **零废话容忍**：每个字都必须影响 AI 的执行决策，否则删掉
- **自适应长度**：单点改动 = 3-5 行（目标+验收）；架构改动 = 完整 6 模块

### 模块选择快速参考

| 范围 + 风险 | 需要哪些模块 |
|-------------|-------------|
| 单点 + 低风险 | 目标+验收 |
| 单点 + 高风险 | 关注点 + 改动边界 + 目标+验收 |
| 多文件 + 中风险 | 关注点 + 改动边界 + 上下文 + 目标+验收 + 执行序列 |
| 架构级 + 高风险 | 全部 6 个模块 |

## 输出确认流程

生成规格后，按以下格式展示：

```
执行规格：

---
<生成的规格内容>
---

要按这个执行吗？
- 确认 → 我直接按这个来
- 要改 → 告诉我哪里调整
- 不用 → 规格给你，我不执行
```

## 示例：动态组装效果

### 输入

用户：「帮我改一下用户登录接口，加个验证码」

### Layer 1 收集结果

- context.md: TypeScript + Express + pnpm + vitest
- habits: 「改动最小化」「完成后跑测试」
- bug-memo: 命中「20240115-token-expired-redirect」
- CodeGraph Context: riskLevel=HIGH, 33 callers, 47 affected tests, HTTP chain 5 层

### Layer 2 分析结果

- 明确度: 明确
- 改动范围: 多文件
- 风险等级: HIGH（来自 CodeGraph）

### Layer 3 组装输出

```markdown
## 关注点
- 向后兼容：33 个调用方依赖 login() 返回格式 {token, user, redirectUrl}，签名不能变
- 安全性：验证码需要过期机制（5min）+ 同 IP 频率限制
- 性能：验证码生成同步完成，不引入额外异步依赖

## 改动边界
- 可改：src/api/auth.ts（loginHandler）、新增 src/services/captcha.ts
- 不可碰：src/middleware/rate.ts（rateLimit）、src/middleware/validate.ts 的接口签名
- 链路位置：POST /api/login 第 3 层（handler），上下层接口不变

## 上下文
- 技术栈：TypeScript + Express + pnpm + vitest
- 链路：rateLimit → validateLogin → [loginHandler] → UserService.verify → DB
- 历史踩坑：login 改动曾丢失 redirect 参数（2024-01），确保 redirect 透传不变

## 目标
在 loginHandler 中增加图形验证码校验，验证码错误返回 400。

## 验收
- `pnpm vitest run tests/auth.test.ts` → 全通过
- `curl -X POST /api/login -d '{"email":"a@b.c","password":"x"}'` → 400 + "captcha required"
- `curl -X POST /api/login -d '{"email":"a@b.c","password":"x","captcha":"wrong"}'` → 400 + "invalid captcha"
- 登录成功时 response body 仍包含 redirectUrl 字段

## 执行序列
1. 新建 src/services/captcha.ts（生成+校验接口）→ 单元测试通过
2. loginHandler 中 password check 前插入 captcha 校验 → `pnpm vitest run tests/auth.test.ts` 通过
3. 补充验证码测试（成功/失败/过期/频率限制）→ 全量测试通过

## 历史经验
- 上次踩坑：login() 返回值改动导致 redirect 参数丢失。本次确保返回格式不变。
```

## 注意事项

- **不要输出对模型没有增益的文字**：角色声明（「你是XX工程师」）、鼓励语（「加油」）、总结语（「以上是我的建议」）——全部删掉，一个字都不留
- **验收标准必须可执行**：能复制粘贴到终端跑的命令，或能肉眼在屏幕上确认的行为。「确保安全」不是验收标准
- **长度与复杂度成正比**：单行修改 = 3-5 行规格；架构改动 = 完整 6 模块。不要把简单任务写复杂
- **保留用户原意**：规格是补充数据和约束，不是改变用户想做的事
- **上下文是注入的，不是复述的**：不要说「根据你的 context.md，你的项目是...」，直接把信息填进对应模块
- **找不到就标注**：如果搜不到相关代码，在规格中注明「→ 执行时先搜索定位」
- **与 arise-router 配合**：如果是 router 路由过来的，直接读 codegraph-context.json，不需要重复调用 CodeGraph
