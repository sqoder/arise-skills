# 提示词优化器

输入一句话（如「帮我检查这个项目的代码」），自动转化为结构化、高质量的提示词。展示给你确认后执行。

## 何时触发

- 用户输入 `/arise-prompt` + 一段描述
- 用户说「帮我优化这个提示词」「把这个变成提示词」「prompt 一下」
- 用户给出一段模糊的任务描述，想要更精确的执行方案

## 工作流程

```
用户输入简短描述
  ↓
识别场景类型（代码审查 / Bug排查 / 功能开发 / 通用）
  ↓
按对应模板生成优化提示词
  ↓
展示给用户：「优化后的提示词如下，要按这个执行吗？」
  ↓
用户确认 → 按提示词执行
用户要改 → 调整后执行
用户说不用 → 只输出提示词文本，不执行
```

## 场景识别

根据用户输入中的关键词判断场景：

| 场景 | 触发关键词 |
|------|-----------|
| 代码审查 | 检查、审查、review、看看代码、代码质量、有没有问题 |
| Bug 排查 | 报错、bug、不工作、为什么、挂了、崩了、异常、500 |
| 功能开发 | 写一个、实现、加个功能、重构、开发、做一个、新增 |
| 通用 | 以上都不匹配时 |

如果无法确定，按**通用**处理。

## 代码定位（涉及代码改动时必做）

当用户输入涉及具体代码（如「改一下登录接口」「这个函数有 bug」「重构这个模块」）时，在生成提示词**之前**先定位相关代码：

1. **搜索定位**：根据用户提到的关键词（接口名、函数名、文件名、模块名）在项目中搜索对应代码。
2. **列举相关代码**：在优化后的提示词中附上：
   - 涉及的文件路径
   - 关键函数/类/接口名
   - 当前代码片段（关键部分，不是整个文件）
3. **填入提示词**：把定位结果作为上下文填进生成的提示词里，让执行时不用再次搜索。

示例：

```
用户输入：「帮我改一下用户登录接口，加个验证码」

优化后的提示词：

## 目标
修改用户登录接口，增加图形验证码校验。

## 相关代码
- `src/api/auth.ts` → `login()` 函数（第 23-45 行）
- `src/middleware/validate.ts` → `validateLogin()` 中间件
- `src/routes/auth.routes.ts` → POST `/api/login` 路由定义

## 当前实现
```ts
// src/api/auth.ts:23
export async function login(req, res) {
  const { username, password } = req.body;
  // ... 当前无验证码校验
}
```

## 要求
1. 在 login() 中增加验证码校验逻辑
2. 验证码错误返回 400 + 明确提示
3. 不破坏现有登录流程
```

**原则：**
- 只列关键代码，不要贴整个文件
- 文件路径 + 行号 + 函数名，让执行时能直接定位
- 如果搜不到对应代码，在提示词中注明「未找到相关代码，执行时先搜索」

## 提示词模板

### 代码审查

```markdown
## 角色
你是一位资深代码审查员，擅长发现安全漏洞、性能瓶颈和可维护性问题。

## 目标
对 <目标文件/模块/项目> 进行全面代码审查。

## 审查维度
1. **安全性**：注入、越权、敏感信息泄露、依赖漏洞
2. **性能**：N+1 查询、内存泄漏、不必要的计算、缓存缺失
3. **可读性**：命名、注释、函数长度、职责单一
4. **规范性**：项目现有风格一致性、lint 规则、类型安全
5. **健壮性**：边界条件、错误处理、空值防御

## 输出格式
按严重度排列：
- 🔴 严重（必须修）：安全/数据丢失风险
- 🟡 建议（应该修）：性能/可维护性
- 🟢 优化（可以修）：风格/命名/小改进

每条包含：文件位置 + 问题描述 + 修复建议
```

### Bug 排查

```markdown
## 角色
你是一位调试专家，擅长系统性排查问题根因，而非头痛医头。

## 症状
<用户描述的现象、报错信息、触发条件>

## 排查要求
1. **复现**：确认触发条件和复现路径
2. **定位**：从报错点向上追溯，找到真正的根因（不是表象）
3. **修复**：给出最小改动方案，说明为什么这样改
4. **防回归**：列出以后改相关代码时需要注意的检查项

## 约束
- 先查 .arise/bug-fix-memory/ 是否有历史记录
- 不要猜测，用证据（日志、断点、测试）说话
- 修复后必须验证：跑相关测试确认问题消失
```

### 功能开发

```markdown
## 角色
你是一位高级工程师，注重代码质量和架构一致性。

## 需求
<用户描述的功能>

## 执行要求
1. **理解现状**：先看现有代码结构和模式，不要凭空造轮子
2. **最小改动**：优先复用现有组件/工具函数，不引入不必要的新依赖
3. **拆解步骤**：把功能拆成可验证的小步骤，逐步实现
4. **验收标准**：
   - [ ] 功能正常工作（描述预期行为）
   - [ ] 不破坏现有功能（跑现有测试）
   - [ ] 代码风格与项目一致
   - [ ] 边界情况有处理

## 约束
- 改动范围尽量小，不做额外重构
- 遵循项目现有的目录结构和命名规范
- 完成后跑 lint + typecheck
```

```markdown
## 角色

## 目标

3. ...

## 输出要求
- <期望的输出形式：代码/文档/列表/分析>

```

## 输出确认流程

生成提示词后，按以下格式展示：

```
📋 优化后的提示词：

---
<生成的提示词内容>
---

要按这个执行吗？
- 确认 → 我直接按这个来
- 要改 → 告诉我哪里调整
- 不用 → 提示词给你，我不执行
```

## 注意事项

- **不要过度复杂化**：如果用户的描述已经够清晰，只做轻度优化，不要硬套模板。
- **保留用户原意**：优化是补充结构和细节，不是改变用户的意图。
- **上下文感知**：如果当前对话已经有项目信息（语言、框架、目录结构），把具体信息填进模板，不要留占位符。
- **简洁优先**：提示词不是越长越好，去掉废话，每句话都要有信息量。
- **可执行**：生成的提示词必须是 AI 能直接执行的指令，不是泛泛的描述。
